## Phase 1 — Event Naming Standardization

**Priority:** 🔴 Release-blocking
**Package:** `core`, `shared`
**Why:** Mixed conventions (`lock_acquired` vs `lock:update` vs `task:plan-ready`) create silent mismatches when new consumers subscribe to events. A bug could go undetected because the subscriber used the wrong separator.

### Problem

Three different conventions exist across the same event bus:

| Location | Convention | Examples |
|---|---|---|
| `LockRegistry` internal | `snake_case` | `lock_acquired`, `lock_released`, `lock_deadlock` |
| `WsBroadcaster` outbound | `colon:namespace` | `lock:update` |
| `TaskOrchestrator` | `colon:namespace` | `task:plan-ready`, `agent:update` |

### Decision

Adopt **`colon:namespace`** (`namespace:event`) everywhere — it matches the orchestrator and broadcaster, which are the primary event sources.

### Changes

**`packages/core/src/locks/lock.registry.ts`**
- Rename emitted events:
  - `lock_acquired` → `lock:acquired`
  - `lock_released` → `lock:released`
  - `lock_deadlock` → `lock:deadlock`

**`packages/core/src/server/ws.broadcaster.ts`**
- Update any listener registrations for lock events to match new names.

**`packages/shared/src/websocket.types.ts`**
- If lock event names are serialized in `ServerMessage` payloads, update the string literals.

**All test files referencing old event names**
- `lock.registry.test.ts` — update event name assertions.

### Acceptance Criteria

- `grep -r "lock_acquired\|lock_released\|lock_deadlock"` returns zero results in `src/`
- All lock-related tests pass with new names
- WS broadcaster correctly relays `lock:acquired` / `lock:released` to the CLI

## Phase 2 — Silent Error Audit

**Priority:** 🔴 Release-blocking
**Package:** `core`
**Why:** Silent swallowed errors in snapshot and memory paths mean users can lose rollback capability or have memory silently corrupted without any indication.

### Problem Areas

1. **`packages/core/src/snapshots/snapshot.manager.ts`** — `catch` blocks that `continue` without logging or surfacing errors to the caller.
2. **`packages/core/src/memory/memory.writer.ts`** — write failures not propagated; callers assume success.
3. **`packages/core/src/tools/write_memory.ts`** — catches errors internally, returns `success: false` but the orchestrator doesn't check tool results for memory writes.

### Changes

**`snapshot.manager.ts`**
- Replace bare `catch { continue }` with `catch (err) { this.emit('snapshot:error', { error: err, context }); continue; }`
- Add `snapshot:error` event to the manager's EventEmitter.
- Surface snapshot errors as task warnings (non-fatal, but visible in UI).

**`memory.writer.ts`**
- All `writeFile` calls must be awaited and their errors re-thrown or returned as typed results — never swallowed.
- Wrap in try/catch and return `{ success: false, error: String(err) }` consistently.

**`task.orchestrator.ts`**
- After memory-manager phase completes, check for any `snapshot:error` events accumulated during the run and include them in the `TASK_COMPLETE` payload as `warnings[]`.

**`packages/shared/src/websocket.types.ts`**
- Add optional `warnings?: string[]` field to the `TASK_COMPLETE` server message payload.

**CLI `App.tsx`**
- If `TASK_COMPLETE` contains `warnings`, display them in a yellow warning panel after completion.

### Acceptance Criteria

- `grep -rn "catch {" packages/core/src/` returns zero results
- All catch blocks either re-throw, emit an event, or return a structured error
- Snapshot write failures are visible in the CLI as warnings
- Memory write failures cause the tool to return `success: false` and the agent to retry or report failure

## Phase 3 — Implement `/compact` (Memory Compaction)

**Priority:** 🔴 Release-blocking
**Package:** `core`, `cli`
**Why:** Without compaction, memory files grow unboundedly across sessions. Long-running projects will exceed LLM context windows, causing degraded agent performance. This is a core product claim ("local-first learning").

### Current State

`packages/core/src/commands/handlers/compact.handler.ts` returns a hardcoded stub: `"Compaction NYI"`.

### Design

Memory compaction uses the LLM to summarize each memory file, removing redundant/outdated entries while preserving unique patterns.

```
User types /compact
  → CommandDispatcher → compactHandler()
  → Load all files from .nightfall/memory/
  → For each file:
      → Build prompt: "Summarize and deduplicate these memory entries. Keep unique patterns, remove redundant ones. Output as markdown."
      → Call provider.chat() (single-shot, no streaming needed)
      → Write compacted result back to file
  → Reload memory index
  → Return summary: "Compacted N files. Removed X entries."
```

### Changes

**`packages/core/src/commands/handlers/compact.handler.ts`**
- Replace stub with full implementation:
  ```typescript
  async function compactHandler(ctx: CommandContext): Promise<string> {
    const files = await loadAllMemoryFiles(ctx.config);
    const results = await Promise.all(files.map(f => compactFile(f, ctx.provider)));
    return formatCompactionSummary(results);
  }
  ```
- `compactFile(file, provider)` — sends file content to LLM with compaction system prompt, writes result back.
- `formatCompactionSummary(results)` — returns human-readable diff summary.

**`packages/core/src/memory/memory.manager.ts`**
- Add `compactAll(provider: ProviderAdapter): Promise<CompactionResult[]>` method.
- Add `CompactionResult` type: `{ file: string; before: number; after: number; removed: number }`.

**`packages/core/src/agents/agent.prompts.ts`**
- Add `COMPACT_MEMORY_SYSTEM_PROMPT` — instructs LLM to summarize memory entries in markdown format, preserving all unique learnings.

**`packages/shared/src/memory.types.ts`**
- Add `CompactionResult` type.

**`packages/cli/src/components/SlashOutput.tsx`**
- Render compaction results as a table (file | before | after | removed).

### Acceptance Criteria

- `/compact` runs without error on a project with populated `.nightfall/memory/`
- Output files are shorter than inputs (or equal if nothing was redundant)
- Original files are backed up to `.nightfall/memory/.compact-backup/` before overwrite
- Memory index is reloaded after compaction
- Running a task after compaction still produces correct agent behavior

## Phase 4 — Implement `/clear`

**Priority:** 🔴 Release-blocking
**Package:** `core`, `cli`
**Why:** Users need to reset state for a fresh session. A stub that silently does nothing is misleading.

### Current State

`/clear` handler is a no-op stub.

### Design

`/clear` clears the in-memory task run list and the on-disk `logs/` directory. It does **not** touch memory or snapshots (those have dedicated commands).

```
User types /clear
  → Optional confirmation: "Clear all task history? [y/N]"
  → Delete .nightfall/logs/*.json
  → Reset TaskOrchestrator's internal run list
  → Emit 'history:cleared' event to CLI
  → CLI resets HistoryView to empty state
  → Return: "Task history cleared."
```

### Changes

**`packages/core/src/commands/handlers/clear.handler.ts`**
- Implement `clearHandler(ctx)`:
  - Read all `.json` files in `.nightfall/logs/`
  - Delete them
  - Call `ctx.orchestrator.clearHistory()` (new method)
  - Return count of cleared files

**`packages/core/src/orchestrator/task.orchestrator.ts`**
- Add `clearHistory(): void` — empties the `taskRuns` array.
- Emit `history:cleared` event.

**`packages/core/src/server/ws.broadcaster.ts`**
- Listen for `history:cleared` and send `{ type: 'SLASH_RESULT', payload: { result: '...' } }` to client.

**`packages/cli/src/store/app.actions.ts`**
- Add `HISTORY_CLEARED` action that resets history state.

**`packages/cli/src/components/App.tsx`**
- Handle `history:cleared` server message → dispatch `HISTORY_CLEARED`.

### Acceptance Criteria

- `/clear` deletes all `.nightfall/logs/*.json`
- `HistoryView` shows empty state after clear
- Subsequent `/history` returns empty list
- Running a new task after `/clear` still works correctly
- `/clear` does not affect memory or snapshots

## Phase 5 — Tool Parameter Validation

**Priority:** 🔴 Release-blocking
**Package:** `core`
**Why:** LLMs occasionally produce malformed tool call JSON. Without validation, tools receive garbage parameters and either crash silently or produce corrupt state. A structured validation layer surfaces these as agent-visible errors so the LLM can self-correct.

### Current State

Tools do manual `String(params.path)` casts with no schema enforcement. Invalid parameters are not caught at the registry level.

### Design

Add a `ToolDefinition` schema to each tool and validate at the `ToolRegistry` call site before execution.

```typescript
interface ToolDefinition {
  name: string;
  description: string;
  parameters: ParameterSchema[];  // required/optional, type, description
}

interface ParameterSchema {
  name: string;
  type: 'string' | 'number' | 'boolean';
  required: boolean;
  description: string;
}
```

### Changes

**`packages/core/src/tools/tool.types.ts`**
- Add `ParameterSchema` and `ToolDefinitionWithSchema` types.
- Add `validate(params: Record<string, unknown>): ValidationResult` function type.

**`packages/core/src/tools/tool.registry.ts`**
- In `executeTool()`, before calling the tool implementation:
  1. Look up the tool's `ParameterSchema[]`
  2. Check all required parameters are present and correct type
  3. If invalid: return `{ success: false, error: 'Invalid parameters: missing "path" (string)' }` — the LLM sees this and retries

**Per-tool changes** (add `parameterSchema` export to each):
- `read_file.ts` — `path: string (required)`, `symbol?: string (optional)`
- `write_file.ts` — `path: string (required)`, `content: string (required)`
- `write_diff.ts` — `path: string (required)`, `diff: string (required)`
- `list_files.ts` — `path: string (required)`
- `search_files.ts` — `pattern: string (required)`, `path?: string (optional)`
- `run_command.ts` — `command: string (required)`, `cwd?: string (optional)`
- `read_memory.ts` — `file: string (required)`
- `write_memory.ts` — `file: string (required)`, `content: string (required)`
- `assign_task.ts` — `subtask_id: string (required)`, `instructions: string (required)`
- `request_review.ts` — `summary: string (required)`
- `update_index.ts` — `entries: array (required)`

### Acceptance Criteria

- Calling any tool with a missing required parameter returns a structured error (not a crash)
- The LLM sees the validation error in its tool result and corrects its parameters
- All tools pass their existing tests with schema validation active
- `ToolRegistry` unit test covers the validation path

## Phase 6 — Plan Editor Error Handling

**Priority:** 🟡 Strongly recommended
**Package:** `cli`
**Why:** If `$EDITOR` is unset, crashes, or the user force-quits, `editPlanInEditor` hangs or produces an unhandled rejection. This causes the CLI to stall with no recovery path.

### Changes

**`packages/cli/src/components/PlanEditor.ts`**
- Wrap the `spawn` call in a try/catch.
- Add a 5-minute timeout: if the editor process does not exit within 300s, kill it and return the original unmodified plan with a warning.
- Handle the case where `$EDITOR` is not set: fall back to `nano`, then `vi`, then error message.
- On non-zero exit code: return original plan (don't apply partial edits).

**`packages/cli/src/store/app.actions.ts`**
- Add `PLAN_EDIT_FAILED` action that returns to `awaiting_approval` phase with an error banner.

### Acceptance Criteria

- Unsetting `$EDITOR` shows a friendly error and returns to plan review
- Killing the editor process mid-edit returns the original plan unchanged
- A 5-minute idle editor is automatically killed with a timeout message

## Phase 10 — Token Budget Accuracy

**Priority:** 🟡 Strongly recommended
**Package:** `core`
**Why:** The `4 chars/token` heuristic can over/undercount by 30%+ (especially for code, JSON, or CJK content), causing premature compaction or context overflow.

### Design

Use a tiered estimation approach:
- For Ollama models: if model metadata includes `context_length`, use it directly; estimate tokens by splitting on whitespace and punctuation (≈ 1.3 tokens/word).
- For OpenRouter: use `response.usage.total_tokens` (already tracked) to calibrate the running estimate per session.
- Expose `context_window` in `NightfallConfig` as an override (default: model-appropriate).

### Changes

**`packages/core/src/agents/agent.base.ts`**
- Replace `Math.ceil(text.length / 4)` with `estimateTokens(text, modelId)`.

**`packages/core/src/agents/agent.utils.ts`** _(new file)_
- `estimateTokens(text: string, modelId: string): number`
  - Whitespace-split word count × 1.3 for code-heavy content
  - Fallback to `chars / 4` for unknown models

**`packages/shared/src/config.types.ts`**
- Add `context_window?: number` to `NightfallConfig` (optional override, default per model family).

**`packages/core/src/config/config.defaults.ts`**
- Add sensible defaults: `deepseek-r1:14b` → 16384, OpenRouter models → 32768.

### Acceptance Criteria

- Token estimates within 15% of actual for typical code files (verified against known token counts)
- Config override `context_window` is respected by `agent.base.ts`
- Existing agent tests pass with new estimator

## Phase 16 — Memory Namespacing Per Project

**`packages/core/src/config/config.loader.ts`**
